# 엔지니어링 노트

## Endpoint 기반 mock/production 전환

**현재 구조:** `ui/config/StoreServices.java`와 `checkout/checkout.module.ts`가 endpoint 설정으로 production/mock 구현을 선택한다.

**영향:** 로컬 UI가 mock으로 정상 동작해도 실제 서비스 연동은 검증되지 않았을 수 있다. UI Orders는 endpoint가 없으면 목록을 제공하지 않는다.

**변경 시 확인:** endpoint values, ConfigMap 렌더링, 생성 client, mock과 production 경로 테스트.

## 서비스 간 Helm 연결이 중앙화되어 있지 않음

**현재 구조:** 서비스마다 독립 Helm chart가 있고 UI endpoint 기본값은 비어 있다. umbrella chart나 활성 cross-service values bundle은 없다.

**영향:** 모든 chart를 설치해도 UI→backend, Checkout→Orders 연결이 자동으로 만들어지지 않는다.

**변경 시 확인:** release naming, Kubernetes Service 이름, `app.endpoints.*`, UI/Checkout ConfigMap.

## Checkout Orders endpoint의 조건부 렌더링

**현재 구조:** `checkout/chart/templates/configmap.yaml`은 persistence provider가 `redis`일 때만 `RETAIL_CHECKOUT_ENDPOINTS_ORDERS`를 출력한다.

**영향:** in-memory Checkout에서 Orders URL만 설정하면 실제 Orders가 아니라 `MockOrdersService`가 사용된다.

**변경 시 확인:** provider 조건, 배포된 ConfigMap, end-to-end submit.

## UI Helm values의 중복 Ingress 키

**현재 구조:** `src/ui/chart/values.yaml`에 `ingresses` 키가 두 번 선언되어 있다. YAML parser는 일반적으로 뒤의 값을 유지하므로 앞 선언은 가려진다.

**영향:** 앞 선언을 수정해도 Helm render 결과에는 반영되지 않을 수 있다.

**변경 시 확인:** `helm template` 결과와 단일 `ingresses` 선언 유지.

## Orders 상품 식별자는 계약상 핵심

**현재 구조:** Orders는 `order_items.product_id`에 상품 ID를 저장하고, 주문 관리 화면은 그 ID로 Catalog를 조회해 상품명을 표시한다.

**영향:** Catalog UUID가 아닌 값이 저장되면 과거 주문에는 상품명을 복구할 정보가 없다. UI는 이름을 임의 생성하지 않고 ID로 폴백한다.

**변경 시 확인:** Checkout item mapping, Orders entity/migration, `GET /orders`, Catalog lookup.

## Orders item collection은 순서보다 스키마 안정성을 선택

**현재 구조:** `OrderEntity.items`는 `Set`이며 `@MappedCollection(idColumn = "order_id")`를 사용한다. `product_id`는 목록 키가 아닌 실제 상품 ID만 저장한다.

**영향:** 영속화 후 주문 item의 표시 순서는 보장되지 않는다. 별도 순번 열 없이 상품 ID를 보존하기 위한 현재 선택이다.

**변경 시 확인:** Orders entity, API mapper, persistence 테스트, item 순서에 의존하는 UI.

## 데모 로그인은 UI 세션 경계에 한정됨

**현재 구조:** UI는 Spring Security WebSession으로 `/demo/orders`만 보호한다. 로그인 검증은 Orders의 `/auth/login` API를 사용하며, 회원가입은 `/users`에 BCrypt hash를 저장한다.

**영향:** UI를 통한 Checkout은 로그인 이메일을 주문 배송지에 고정하고 UI 주문 화면은 같은 이메일로 필터링한다. 그러나 Orders API 자체에 토큰 검증은 없으므로 직접 API 호출에서 다른 `customerEmail`을 전달하는 것까지 막지는 않는다.

**변경 시 확인:** 실제 사용자 단위 API 보안이 필요해지면 인증 정보를 Orders까지 전달하는 방식(JWT 또는 service-to-service 인증)을 별도 설계한다.

## Users 마이그레이션은 Orders 시작 시 적용됨

**현재 구조:** `V2__Users.sql`이 `users` 테이블을 정의하고, Orders의 Flyway가 PostgreSQL provider 시작 시 적용한다.

**영향:** RDS 계정에 DDL 권한이 없으면 Orders Pod 시작이 실패할 수 있다. in-memory provider에서는 사용자 계정이 Pod 재시작 뒤 유지되지 않는다.

**변경 시 확인:** RDS endpoint·Secret·DB 권한, Flyway schema history, 새 Pod 기동 로그.

## `ui-backup`의 역할은 확인되지 않음

`src/ui-backup/`은 전체 UI 소스처럼 보이지만 외부 참조를 찾지 못했다. 삭제·빌드·배포 전 소유자 확인이 필요하다.

## 테스트 특성 차이

* UI·Cart·Orders는 JUnit 테스트가 있다. Orders PostgreSQL 테스트는 Docker/Testcontainers가 필요하다.
* Catalog에는 Go 테스트가 있다.
* Checkout에는 Jest 설정이 있지만 기본 `test` script는 `exit 0`이다. 실제 검증에는 `test:integration` 또는 실질적인 unit test script가 필요하다.

## 로컬 Compose는 end-to-end 환경이 아님

Compose 파일은 서비스별 의존성과 host port만 정의한다. 통합 Compose와 endpoint 자동 wiring이 없으므로 여러 서비스를 함께 띄울 때 endpoint를 수동으로 구성해야 한다.
